# 作業說明報告：Loop / Graph 設計與執行反思

本報告對應作業「步驟三」與「步驟四」，說明如何基於 Andrej Karpathy 的 LLM Wiki 模式建構「K-Pop 音樂特徵與熱門歌曲預測」知識庫，並編譯出教學型 HTML 簡報（`slides/index.html`）。

---

## 一、步驟三：Loop / Graph 設計與運作流程

### 1. 整體狀態機流程圖 (Workflow Graph)

```
[Raw 論文輸入] 
      │
      ▼
┌──────────────────────────────────────────────────────────┐
│  Loop 1: 漸進式知識攝取與編譯 (Ingest & Compile Loop × 5)   │
│  1. 讀取 raw/ 論文 → 討論並提煉核心指標與結論               │
│  2. 寫入 wiki/sources/ 單篇筆記                            │
│  3. 更新/新建 wiki/concepts/ 與 wiki/entities/ 雙向連結頁   │
│  4. 檢查新舊文獻衝突 → 更新 wiki/overview.md 綜合論點       │
│  5. 更新 wiki/index.md 目錄 與 wiki/log.md 時間軸          │
└──────────────────────────────────────────────────────────┘
      │
      ▼
┌──────────────────────────────────────────────────────────┐
│  Gate 1: 知識庫健康檢查 (Lint Pass)                       │
│  - 檢查孤島頁面 (Orphan Pages) 與斷裂的 [[Wiki 連結]]       │
│  - 統一數據單位（如歌長統一標註「分:秒」與「總秒數」）         │
└──────────────────────────────────────────────────────────┘
      │
      ▼
┌──────────────────────────────────────────────────────────┐
│  Loop 2: 簡報規劃、事實核對與生成 (Query & Slide Loop)      │
│  1. 查詢 wiki/index.md 與 overview.md 規劃 10 頁教學大綱    │
│  2. 深入概念頁提取具體數據（AUC、Valence、前奏秒數）          │
│  3. [Verification Check] 逐項核對數字是否可追溯至 sources/  │
│     ├─ 若數據缺失或單位不一致 ──► 退回 Wiki 補齊/修正        │
│     └─ 若驗證通過 ──► 生成互動式教學簡報 slides/index.html   │
└──────────────────────────────────────────────────────────┘
```

### 2. 關鍵設計細節說明
- **哪些步驟會重複執行？**
  1. **Ingest & Compile Loop（重複 5 次）**：每加入一篇論文（Paper 01 至 Paper 05），AI 都必須重複執行「精讀筆記 → 更新概念頁 → 修正總覽頁 → 更新 `index.md` 與 `log.md`」的完整迴圈，讓知識像複利一樣逐篇疊加。
  2. **Slide Verification Loop（迭代檢查）**：在產出 HTML 簡報大綱與內容時，針對每一頁投影片的數據與結論進行逐頁核對，若發現與 Wiki 記載不符則重新生成該頁區塊。
- **哪些地方需要檢查或重新生成？**
  - **跨論文指標單位統一**：例如 Paper 03 同時出現「3 分 32 秒」與「212 秒」，Paper 01 出現 $R^2$ 而 Paper 05 使用 AUC。在 `Lint` 階段需檢查並統一標註格式，避免簡報圖表混用不同尺度。
  - **HTML 簡報視覺與互動邏輯**：產出 `slides/index.html` 後，需檢查長條圖寬度百分比是否與 Wiki 數值（如 Melon 0.62 vs. Spotify 0.79）精準對應，以及隨堂測驗互動按鈕是否正常運作。
- **為什麼這樣設計？（相較於傳統 RAG 的優勢）**
  - 若直接把 5 篇論文丟給 LLM 生成簡報，模型很容易只挑第一篇或最後一篇的重點，甚至混淆 Melon 與 Spotify 的數據。透過 **「先編譯 Wiki（建立 `overview.md` 對照表）→ 再讀取 Wiki 生成簡報」** 的兩階段架構，把「知識整合」與「簡報排版」解耦，大幅降低幻覺率並確保每頁都有明確的 `[[wiki-ref]]` 溯源標籤。

## 二、步驟四：執行反思 (Reflection)

### 1. 哪一個節點最常出錯？
- **「跨文獻更新 `overview.md` 與概念頁（Cross-Reference & Synthesis）」** 這一節點最常出錯。
- 具體問題在於：當攝取到第 4 篇（跨文化偏好差異）與第 5 篇（多模態預測）時，AI 容易只把新結論「附加在檔案最下方」，而忘記回頭修改前面章節的舊論述（例如 Paper 01 提到「音訊特徵分類準確率達 88%」，但 Paper 05 指出「純音訊爆紅預測 AUC 僅 0.74」），導致同一份 Wiki 內出現表面上的數據矛盾，若未解釋清楚（進榜二元分類 vs. 病毒式爆紅預測的任務定義差異），讀者在看簡報時會感到困惑。

### 2. 發現問題後，把檢查往前移到了哪一個步驟？
- 我將「數據一致性與定義對齊檢查」從原本的 **「簡報生成後的人工檢查」**，大幅前移到 **「每次 Ingest 結束時的 `overview.md` 更新步驟」**，並在 `AGENTS.md` Schema 中明文規定：
  > *「每次 Ingest 新論文時，若新數據與既有頁面存在表面張力，必須立即在 `overview.md` 與概念頁中補上『任務定義或市場差異說明』，不可留到產出階段才處理。」*

### 3. 有沒有因此修改 Workflow / Graph？為什麼？
- **有，做了兩項關鍵修改**：
  1. **在 Ingest Loop 與 Slide Generation 之間新增獨立的 `Lint Pass` 節點**：強制在生成簡報前先跑一次全庫健康檢查，確認所有 12 個 Wiki 頁面都有雙向連結、且所有百分比/秒數單位一致。
  2. **在簡報生成流程加入 `Verification Gate（事實核對閘門）`**：規定每張投影片底部必須附上對應的 `[[wiki-ref]]` 來源標籤（如 `[[concepts/tiktok-effect]]`）。這迫使模型在寫每一頁 HTML 時都必須回查對應的 Wiki 頁面，從結構上杜絕憑空捏造數據的問題。
